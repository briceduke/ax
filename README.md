# Using ax in a project

4 October 2026. This page is the how-to for **0.1.0**. The intended system, with done / partial / not yet on every piece, is [docs/target.md](docs/target.md).

**Implemented:** `ax log`, `ax check`, `ax compile` (deterministic assembler). **Not implemented:** `ax init`, `ax adopt`, `ax eval`, `ax ablate`, `ax retro`, packs, upgrades, `ax doctor`.

ax keeps a small durable core in your product repo. You edit that core. Adapters for Cursor and Claude Code are generated. Do not edit the generated files.

## Install

From this repo, put `ax` on your PATH. Hooks call `ax check --tier fast`, so the binary name must be `ax`.

```powershell
go install github.com/briceduke/ax/cmd/ax@latest
```

Or build a local binary and copy it somewhere on PATH:

```powershell
go build -o ax.exe ./cmd/ax
```

`ax.yaml` pins `0.1.0`. A newer binary warns; it does not fail.

## Start a project by hand

`ax init` does not exist yet. In the product repo:

1. Write `ax.yaml`:

```yaml
ax: 0.1.0
targets: [cursor, claude-code]
packs: []
```

2. Add `.gitignore` with `.ax/`, and `.gitattributes` with `* text=auto eol=lf`.
3. Create empty dirs: `core/capabilities`, `core/scaffolds`, `log/decisions`, `log/observations`, `log/friction`.
4. Write `core/intent.md` under one page. Headings that matter: what is being built, for whom, values, taste, process weight.
5. Add `core/checks.yaml` with the three builtins (copy from [testdata/fixtures/software/core/checks.yaml](testdata/fixtures/software/core/checks.yaml)). Point `enforces` at the decision you write next.
6. Record that you adopted ax:

```powershell
ax log decision "adopt ax for harness management"
```

Fill Context, Options, Choice, Why. Then:

```powershell
ax compile
ax check
```

`ax` finds `ax.yaml` by walking up from the current directory.

## What you edit

| Path | Role |
| --- | --- |
| `core/intent.md` | The only long-lived prose. |
| `core/capabilities/*.md` | What the project wants done, regardless of model strength. |
| `core/scaffolds/*.md` | Temporary crutches. Each names the weakness and when to delete it. |
| `core/checks.yaml` | Executable rules. |
| `log/decisions/`, `log/observations/`, `log/friction/` | One file per entry. Never edit a decision; write a new one that supersedes it. |

## What compile owns

`ax compile` writes adapters and `.generated/manifest.yaml`. Markdown adapters start with `generated by ax. do not edit`.

| Core | Cursor | Claude Code |
| --- | --- | --- |
| Intent, scaffolds, unhinted capabilities | `AGENTS.md` | `CLAUDE.md` |
| Capability hint `user-invocable` | `.cursor/commands/{id}.md` | `.claude/skills/{id}/SKILL.md` |
| Capability hint `isolation` | `.cursor/agents/{id}.md` | `.claude/agents/{id}.md` |
| Fast-tier checks | `.cursor/hooks.json` after file edit | `.claude/settings.json` after Write/Edit |
| Tools (none in core yet) | `.cursor/mcp.json` | `.mcp.json` |

Compile hashes intent, capabilities, scaffolds, `checks.yaml`, and the target specs. A second compile with the same hash skips. `--target cursor` compiles one tool. `--without verify-pinouts` drops that scaffold and writes into `.ax/worktrees/`.

If you change the core, compile again. If you edit an adapter by hand, `ax check` fails. Fix the core, then compile.

## Daily loop

```powershell
ax log friction "agent re-derived the battery math from scratch"
ax log observation "4.1 mA while recording" --method "ammeter on the dev board"
ax log decision "detent twist is the power switch"
ax compile
ax check
```

Pipe a drafted decision body on stdin. `--supersedes <id>` records the older decision it replaces.

`ax check` default tier is `full` (fast plus full). `--tier fast` is what hooks run. `--tier slow` adds slow checks. `--all` ignores the pass cache in `.ax/`.

A failed check prints the last output lines, then `enforces <path>` and that decision's Why.

## File shapes

Capability:

```markdown
---
id: record-decision
kind: capability
when: a choice between real alternatives gets made
hints: [user-invocable]
---

Write a dated entry: context, options considered, choice, why.
```

No hints means it is always on and lands in `AGENTS.md` / `CLAUDE.md`. Unknown frontmatter fields are errors.

Scaffold:

```markdown
---
id: verify-pinouts
kind: scaffold
compensates: model invents pin assignments not in the datasheet
added: 2026-10-02 (friction/2026-10-02-wrong-pin)
retire_when: eval pinout-recall passes 5/5 without it
---

Before assigning a pin, quote the datasheet table row it comes from.
```

`added` must point at an existing friction file or `ax-consistency` fails.

Your own check in `core/checks.yaml`:

```yaml
- id: board-fits-case
  run: python checks/fit.py
  inputs: [interfaces/envelope.yaml, hardware/case/**, pcb/**]
  tier: full
  enforces: log/decisions/2026-10-04-envelope-v1
```

Exactly one of `run` or `builtin`. `run` is split into argv and executed with no shell. `inputs` are globs; the check is skipped when its definition and those files have not changed since the last pass.

Log limits: decisions at most 60 lines, with `## Context`, `## Options`, `## Choice`, `## Why`. Observations at most 30 lines. Friction is one line.

## Built-in checks

- `ax-format` — log entries, capabilities, and scaffolds parse and match their schemas.
- `ax-consistency` — `enforces` and `supersedes` resolve; a superseded decision is not enforced; each scaffold's `added` link exists.
- `ax-staleness` — generated adapters match the core hash. With targets enabled and no manifest: run `ax compile`.
